## Методика

Сценарий `tools/benchmark_local.py` повторяет разбор окончательных фраз
сохранённого сеанса через LiveReferencePipeline и отдельно подаёт PCM-аудио
в SherpaStreamingRecognizer без ожидания реального времени. Он сохраняет
команду, версию Python, commit, хэши входных файлов и модели, времена и профиль.
Первый проход содержит прогрев. cProfile запускается отдельно и его времена
не используются для сравнения скорости: профилирование добавляет накладные расходы.
Синтетические времена вызовов парсера идут с интервалом 10 секунд; времена слов
ASR сохраняются. Это тест отдельных этапов, а не полный replay богослужения.

Исходные сеансы находятся в
`C:/Users/fores/AppData/Local/LiVerse/logs/vosk_probe`.
Первый: `20260927_114727_401555` (31 секунда, одна непустая фраза).
Контрольный: `20260927_114819_000975` (три непустые фразы).

Команда из корня репозитория в PowerShell:

```powershell
.venv/Scripts/python.exe tools/benchmark_local.py --session C:/Users/fores/AppData/Local/LiVerse/logs/vosk_probe/20260927_114727_401555 --model .cache/liverse/models/vosk-model-small-streaming-ru-0.54 --output .cache/liverse/benchmarks/repeat-baseline.json --repeats 3 --threads 1
```

Для контрольного сеанса замените `--session`, добавьте `--skip-audio` и выберите
новое имя отчёта. Для экспериментального прогона добавьте `--regex-cache 8192`.
Этот параметр меняет внутренний кэш Python только в тестовом процессе:
это диагностический эксперимент, не предложенный production-фикс.
Повторное использование имени существующего отчёта запрещено.

## Причина и границы вывода

В обычном профиле одной фразы выполнено 5774 компиляции regex.
Время внутри re._compile составляет 3.44 из 3.77 секунды профилированного
вызова (это вложенные времена, их нельзя складывать).
normalize_text повторно проходит ASR_REPLACEMENTS, а book_candidates строит
шаблон для каждого варианта названия книги. Повторные обращения вытесняют
шаблоны из ограниченного кэша. Увеличение кэша воспроизводимо устраняет
большую часть задержки на проверенных фразах.

Это подтверждённое узкое место исходников 1.2.9. Журналы работающей 1.2.10
показывают схожий порядок задержек парсера (1.1–1.6 с), однако её упакованный
код напрямую этим сценарием не профилировался. Полного сравнения двух
версий и режимов hybrid / smart slide / Holyrics пока нет.

Следующий шаг: заранее скомпилировать стабильные наборы шаблонов, проверить
все регрессионные случаи парсера и повторить измерения. Возраст процессора
усиливает накладные расходы, но основной найденный эффект программный.

## Патч предварительной компиляции

раз при загрузке parser.py и сохраняются в модуле. Порядок замен, флаги,
границы совпадений и алгоритм нечёткого поиска сохранены. Глобальные параметры
кэша Python в рабочем приложении не изменяются.
