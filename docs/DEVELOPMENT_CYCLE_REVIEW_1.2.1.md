# Разбор цикла разработки и выпуска LiVerse 1.2.1

Дата разбора: 2026-09-01.

## Итог цикла

Выпуск `1.2.1` собран из коммита `37a414e`, проверен в Debian и Windows,
опубликован в GitHub Releases. Прошли:

- 257 тестов в Debian;
- 257 тестов в Windows;
- проверка упакованных исполняемых файлов и обязательных ресурсов;
- чистая установка, запуск и удаление;
- обновление установщиком с `1.2.0` до `1.2.1` с сохранением данных;
- проверка размера и SHA-256 до и после переноса;
- проверка метаданных GitHub и обнаружения версии `1.2.1` обновлятором.

После выпуска перенос через флешку оформлен отдельным скриптом в коммите
`5f0d289`.

Пользователь оценил общий расход этого цикла со вчерашнего дня в 15% недельного
лимита токенов. Точного счётчика по отдельным операциям нет, поэтому ниже
указана качественная оценка потерь, без вымышленных процентов.

## Что уже автоматизировано хорошо

### Разработка на Debian

- связанные тесты можно запускать отдельно;
- полный набор запускается командой `make test`;
- версия приложения хранится в одном Python-модуле;
- Git показывает точный состав изменений перед коммитом.

### Windows VM

Команда

```bash
make windows-release VERSION=1.2.1 \
  PREVIOUS_INSTALLER=/путь/к/LiVerse-Setup-1.2.0.exe
```

сама передаёт проверенный снимок исходников в офлайн-VM и выполняет Windows-
тесты, сборку PyInstaller, создание установщика Inno Setup, чистую установку и
обновление поверх предыдущей версии.

### Перенос результата

Теперь вместо длинных команд используются:

```bash
tools/transfer_windows_release_via_usb.sh to-usb VERSION
tools/transfer_windows_release_via_usb.sh from-usb VERSION MOUNTPOINT
```

В обоих направлениях установщик проверяется по SHA-256. SHA-256 — это короткий
цифровой отпечаток файла: совпадение подтверждает, что при переносе файл не
изменился.

## Узкие места последнего цикла

### 1. Обратный перенос из Windows VM

Это было главное организационное узкое место. ISO оказался пригоден только для
передачи `Debian → Windows`: виртуальный CD-ROM доступен Windows только для
чтения. Попытка читать установщик через QEMU Guest Agent крупными блоками
упиралась в тайм-аут. Возврат к флешке потребовал нескольких ручных переключений.

Исправление уже сделано: удачная последовательность сохранена в
`tools/transfer_windows_release_via_usb.sh`. Непреодолимыми пока остаются только
два ручных действия: перенаправить флешку в VM и вернуть её Debian.

### 2. Повторные полные Linux-тесты

Во время подготовки версии полный набор был запущен вручную, а затем ещё раз
внутри `make windows-release`. Второй прогон полезен как часть окончательной
проверки конкретного коммита, но первый непосредственно перед ним можно не
делать, если связанные тесты уже зелёные и следующим шагом сразу идёт строгая
выпускная команда.

### 3. Жёстко записанный номер версии в тестах и документации

После изменения `1.2.0` на `1.2.1` два теста ожидаемо продолжали требовать
старый номер. Это вызвало ещё один полный прогон. Номер также приходится менять
в README и Inno Setup.

Предлагаемое улучшение: перед следующим выпуском добавить одну небольшую команду
изменения версии, которая обновляет только заранее перечисленные места и сразу
запускает проверку согласованности. Создавать её следует перед следующим
реальным повышением версии, а не заранее ради самой автоматизации.

### 4. Слишком ранняя отправка `main` на GitHub

В этом цикле коммиты были отправлены до окончательной Windows-сборки. Если бы
Windows-проверка упала, ветка `main` уже содержала бы непроверенный кандидат.

Оптимальный порядок: локальный чистый коммит → строгая Windows-проверка → push
в `main` → GitHub Release. Тег выпуска должен указывать именно на проверенный
коммит.

### 5. Долгая загрузка установщика на GitHub

Передача примерно 167 МиБ заняла несколько минут и не показывала процент.
Ускорить медленное интернет-соединение средствами проекта нельзя. Важно не
прерывать активную загрузку и не запускать её повторно. Проверенный локальный
файл в `.windows-release/VERSION` позволяет повторить только публикацию, не
повторяя Windows-сборку и перенос.

### 6. В одном разговоре смешались три разных режима работы

Сначала исправлялись дефекты, затем готовилась версия, затем переносился и
публиковался установщик. Из-за этого становилось сложнее понимать, какие
проверки уже относятся к окончательному коммиту.

Лучше явно разделять:

1. разработку и локальную проверку;
2. создание кандидата выпуска;
3. публикацию уже проверенного кандидата.

## Предлагаемый оптимальный цикл

### Этап A. Одна небольшая задача

1. В начале сообщить один наблюдаемый дефект или одно улучшение.
2. Приложить последний журнал, точную последовательность действий и ожидаемый
   результат.
3. Сначала потребовать воспроизведение и объяснение причины.
4. Разрешить минимальный патч и связанные тесты.
5. Проверить результат вручную на Debian. Для Windows-зависимого поведения — в
   VM.
6. Сделать отдельный локальный коммит. Не повышать версию после каждой мелочи.

### Этап B. Накопление кандидата

Повторять этап A для следующих независимых проблем. `main` можно отправлять на
GitHub после зелёных обычных тестов, но выпуск и установщик пока не создавать.
Перед воскресным использованием желательно прекратить добавление новых функций
и оставить время только на исправление критических дефектов.

### Этап C. Выпуск

1. Зафиксировать состав версии и больше не добавлять новые возможности.
2. Изменить номер версии и CHANGELOG одним отдельным коммитом.
3. Запустить связанные проверки версии, но не дублировать полный `make test`.
4. Из чистого локального `main` выполнить одну строгую команду
   `make windows-release ...`; она сама выполнит полный набор Debian и Windows.
5. Если всё зелёное — отправить проверенный коммит на GitHub.
6. Перенести установщик двумя сохранёнными USB-командами.
7. Опубликовать GitHub Release и проверить размер, SHA-256, целевой коммит и
   обнаружение обновлятором.

## Какую версию устанавливать сейчас

На рабочий церковный компьютер следует устанавливать `1.2.1`. Намеренно
ставить туда старую `1.2.0` только ради эксперимента не стоит.

Проверка обновлятора состоит из двух уровней:

- автоматическая проверка уже подтвердила, что `1.2.0` видит выпуск `1.2.1`,
  правильный размер и SHA-256;
- отдельный полный опыт «скачать и установить обновление из интерфейса» полезен
  один раз на тестовой Windows с интернетом, но не обязателен перед установкой
  уже проверенного `1.2.1` на рабочий компьютер.

VM специально работает без интернета, поэтому ради этого опыта не следует
подключать её к сети и рисковать незапланированным обновлением Windows. Если на
каком-либо отдельном тестовом компьютере уже установлена `1.2.0`, там можно
проверить обновлятор естественным способом.

## Шаблоны промптов для следующего цикла

### Диагностика без исправления

```text
LiVerse, ветка main. Наблюдаемый дефект: <что произошло>.
Шаги: <короткая последовательность>.
Ожидалось: <результат>.
Фактически: <результат>.
Журнал: <точный путь>.
Сначала воспроизведи, найди причину и проверь историю этого кода.
Пока ничего не исправляй, не коммить и не push.
```

### Минимальное исправление

```text
Исправь подтверждённую причину минимальным патчем.
Не рефакторь соседний код. Добавь регрессионный тест, сначала запусти связанные
тесты. Полный набор пока не запускай. Покажи diff и результат тестов; не push.
```

Регрессионный тест — это проверка, которая воспроизводит уже найденную ошибку и
не позволяет ей незаметно вернуться позже.

### Подготовка кандидата выпуска

```text
Подготовь кандидата LiVerse <VERSION> из текущего main.
Сначала проверь git status и состав изменений. Обнови номер версии и CHANGELOG,
запусти связанные проверки версии и сделай локальный коммит. Не push и не
публикуй. Покажи готовую команду строгой Windows-сборки.
```

### Полный выпуск

```text
Выпускаем LiVerse <VERSION>. Предыдущий официальный установщик: <PATH>.
Запусти строгую Windows-сборку из чистого локального main. Если любой тест
упадёт — остановись и ничего не публикуй. Если всё зелёное — сообщи результаты,
затем push, перенос сохранённым USB-скриптом и GitHub Release. В конце проверь
SHA-256, размер, целевой коммит и работу обновлятора.
```

## Следующее возможное улучшение автоматизации

Наиболее полезное следующее улучшение — не новая система сборки, а одна команда
публикации уже импортированного кандидата. Она должна проверять существующий
файл в `.windows-release/VERSION`, его SHA-256, чистоту Git, наличие проверенного
коммита и только затем вызывать GitHub Releases. Делать её имеет смысл при
следующем выпуске, когда последовательность повторится второй раз.
