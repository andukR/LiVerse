# Набор проповедей Rodnik для обучения риск-модели LiVerse

## Цель

Собрать **живые** примеры для Sherpa 0.54, на которых модель риска решает:
показать найденную ссылку сразу или сначала попросить подтверждение.

Здесь «рискованный случай» — это предложенный LiVerse показ, который оказался
неверным или сомнительным. Это не любой отрывок без библейской ссылки.

## Почему нужен новый набор

Данные старого Vosk 0.22 не следует автоматически смешивать с Sherpa 0.54:
модели по-разному искажают названия книг, числа, паузы и уверенность слов.
Для Sherpa в начале работы набора было 167 безопасных автопоказов и только 8
случаев, требующих подтверждения. Этого недостаточно для безопасного
переобучения наивного байесовского алгоритма.

## Границы первой версии

- Используем существующий tools/replay_audio_files.py, а не второй эмулятор.
- Каждый ролик связываем с аудио и субтитрами по YouTube video_id.
  video_id — постоянный 11-символьный идентификатор ролика в его ссылке.
- Субтитры являются только указателем времени. Истиной для разметки остаётся
  результат Sherpa и LiVerse по аудио.
- Синтетические примеры не входят в рабочую риск-модель. Их можно применять
  для тестов правил разбора.
- Никакая новая модель не заменяет текущую без проверки на проповедях, которые
  не участвовали в обучении.

## Этапы

### 1. Инвентаризация без сети и без распознавания

Для каждого найденного video_id определить:

- есть ли локальное аудио;
- есть ли локальные субтитры;
- есть ли оба файла;
- чего именно не хватает.

Результат: небольшой отчёт, по которому можно выбрать первую ограниченную
партию роликов.

### 2. Докачка только недостающих субтитров

Если у аудио есть video_id, но нет субтитров, сначала пробуем скачать только
ручные или автоматически созданные субтитры YouTube. Аудио на этом шаге не
скачивается.

Перед сетевым запуском скрипт обязан сначала показать список роликов и число
запросов. Массовая загрузка требует отдельного подтверждения пользователя.

### 3. Отбор коротких окон по субтитрам

Из субтитров формируются временные окна трёх типов:

1. Адресные: рядом со словами «стих», «глава», «послание», «евангелие»,
   «псалом» (включая типичные ASR-варианты «пса лом» и «сало» с номером),
   «пророк», «книга», «прочитаем», «откроем» и названиями книг Библии.
   Одного такого слова недостаточно: рядом должно быть число либо адрес,
   который уже способен разобрать LiVerse.
2. Текстовые: фразы субтитров, похожие на текст Библии по уже существующему
   поиску LiVerse.
3. Контрольные: немного обычной речи между кандидатами и участки до/после
   цитаты. Они нужны для поиска ложных предложений и повторных срабатываний.

В обычную пачку контрольные окна не входят. Для отдельного аудита выбираются
до трёх контрольных окон по 45 секунд на запись. Они берутся только из
промежутков, не пересекающихся с окнами цитат, и содержат субтитры с обычной
речью, а не слова-маркеры.

Сначала объединяются сами найденные места, если между ними не больше 30 секунд,
и только затем добавляется запас аудио. Для адресных мест это 15 секунд до и
45 секунд после; для совпадения с текстом Библии — 12 секунд до и 15 после.
Так близкие слова больше не соединяют в одно многоминутное окно только из-за
перекрытия добавленного запаса.

### 4. Пакетная эмуляция

Выбранные окна вырезаются из локального аудио и один раз пакетно пропускаются
через существующий replay_audio_files.py с параметрами:

    --asr-engine sherpa-0.54 --citation-detection-mode hybrid_confirm

Окно длиннее двух минут разбивается на части с перекрытием 5 секунд. Это
сохраняет речь на границе частей и не создаёт слишком долгие задания для
распознавания.

Результат: обычные trigger_cases.jsonl. Эмуляция не запускается во время
ручной разметки.

Для рабочей пачки используется один существующий сценарий. Он сам выбирает до
трёх ещё не обработанных записей; в последней пачке их может быть одна или две:

```bash
tools/replay_rodnik_sermons.sh next
tools/replay_rodnik_sermons.sh review
```

`next` (как и ручной `batch`) создаёт изолированную папку с планами окон,
WAV-фрагментами и логами.
После успешной эмуляции запись фиксируется обработанной. `review` читает
указатель только на последнюю полностью завершённую пачку; поэтому
незавершённый прогон не смешивается с её разметкой.

Контрольные окна запускаются отдельно:

```bash
tools/replay_rodnik_sermons.sh audit "/путь/к/проповеди.webm"
```

`audit` не помечает запись обработанной для обычной команды `next`.

### 5. Ручная разметка

Размечаются только реальные предложения LiVerse. Приоритет:

- правильный показ отдельного стиха размечается как верная ссылка, даже если
  перед ним был пропущен соседний стих;
- отсутствующее срабатывание не получает категорию аннотатора: его фиксируют
  отдельным последовательностным регрессионным сценарием;
- для такого сценария сохраняют объявленный диапазон, фактический порядок
  чтения и ожидаемый порядок показанных слайдов.

- обычная речь, ошибочно ставшая ссылкой;
- названная, но неверно разобранная ссылка;
- искажения названий книг и чисел;
- ошибки разбора при достаточном распознавании;
- шум или музыка, если LiVerse предложил слайд.

Правильные случаи также сохраняются, но не должны существенно преобладать.

### 6. Проверка новой риск-модели

Новая модель сравнивается с текущими правилами на отложенных проповедях:
записях, которые не входили в обучение. Выпуск возможен, только если:

- не выросло число ошибочных автопоказов;
- число пропущенных рискованных случаев не выросло;
- польза подтверждена на нескольких независимых записях.

## Ближайший минимальный результат

1. Получить отчёт инвентаризации.
2. Выбрать две записи с аудио и субтитрами для проверки способа отбора окон.
3. Лишь затем делать сетевую докачку или долгую эмуляцию.

## Регрессионный прогон уже обработанных записей

Уже скачанные записи не нужно заново размечать целиком после каждого патча.
Они используются как фиксированный регрессионный набор: тот же аудиофайл
прогоняется новой версией, а оператору показываются только изменившиеся
результаты.

### Состав набора на 17 сентября 2026 года

Основной набор — локальные записи из `.cache/liverse/replay_audio`, для которых
есть завершённый replay-сеанс и сохранены `events.jsonl` или
`trigger_cases.jsonl`. В текущем кэше это 140 скачанных записей, 129 уже
отмеченных как обработанные, 900 файлов срабатываний, 1535 срабатываний и 91
журнал инцидентов УПС. Из срабатываний 1187 размечены, 348 ещё ожидают
разметки. Эти числа являются снимком кэша и должны пересчитываться перед
новым сравнением.

Набор делится на три уровня:

1. **Обязательное ядро** — все ранее исправленные случаи и все записи с
   `smart_slide_incidents.jsonl`. Они проверяют, что известные ошибки не
   вернулись.
2. **Размеченный общий набор** — все завершённые окна с ручной меткой в
   `trigger_cases.jsonl`. Он проверяет распознавание адресов и обычного текста.
3. **Контрольный набор** — отдельные окна обычной речи из `audit`, не
   участвовавшие в обучении. Он нужен для контроля ложных срабатываний.

Неразмеченные случаи не используются как эталон истины: после повторного
прогона они попадают только в список на ручную проверку.

### Метрики сравнения

- **Точность ссылки:** доля размеченных ссылок, для которых новая версия
  сохранила правильную книгу, главу и диапазон.
- **Ложные срабатывания:** обычная речь или неверный адрес, на котором новая
  версия предложила показ.
- **Пропуски:** известный правильный адрес или стих, который новая версия не
  показала.
- **Списки и диапазоны:** совпадение состава списка и границ диапазона без
  превращения двух адресов в один.
- **УПС:** число неверных переходов, пропусков стихов, перескоков и повторных
  показов; отдельно измеряется задержка перехода относительно первого
  подтверждённого текста стиха.
- **Стабильность:** доля случаев, в которых результат новой версии совпал со
  старым результатом; изменение результата считается полезным только при
  наличии подтверждённой причины.

Перед выпуском новая версия не должна ухудшать обязательное ядро и контрольный
набор. Улучшения на неразмеченных окнах сначала требуют ручного подтверждения.

### Автоматическое сравнение двух прогонов

Для сравнения сохранённой старой и новой пачки используется существующий
сравниватель:

```bash
.venv/bin/python tools/compare_replay_results.py \
  .cache/liverse/rodnik_replay_batches/OLD_BATCH \
  .cache/liverse/rodnik_replay_batches/NEW_BATCH
```

Можно передать папку `logs` или отдельную папку одного прогона. Отчёт выводит
только добавленные, исчезнувшие и изменившиеся случаи. Для машинной обработки
доступен ключ `--json`.

Случай сопоставляется по исходной записи, границам аудио-окна и времени
срабатывания. Сравниваются ссылка, источник распознавания, список ссылок,
уровень риска, факт и результат показа. Число инцидентов УПС сравнивается
отдельно, потому что остановка браузерной эмуляции оператора не обязана иметь
точно такой же момент в двух запусках.

Полный рабочий конвейер пилотной проверки запускается в режиме предварительного
плана:

```bash
.venv/bin/python tools/run_replay_regression.py --scope pilot --limit 3
```

Он выбирает три существующих плана, создаёт манифест и не запускает тяжёлое
распознавание. После проверки манифеста выполняется:

```bash
.venv/bin/python tools/run_replay_regression.py --scope pilot --limit 3 --run
```

Для обязательного ядра используется `--scope core`, а для всех найденных
планов — `--scope all`. Каждый новый результат сохраняется в отдельной папке
`.cache/liverse/replay_regressions`; старые логи не перезаписываются.
